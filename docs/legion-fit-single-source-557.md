# 军团 3D 取景：层高单一来源修复（`.557`）与未消方差（`.557` 后仍在）

> 状态：**修复已上线**（`0.6.4-preview.557` / `e3067f3b`）；**取景方差未消除**，已在下方如实记录为残余第 10 条。
> 复跑命令见文末，所有数字都由同一支探针产出。

## 1. 缺陷：取景用的层高与绘制用的层高不是同一个来源

```
绘制：nodeToVec3({...node}, 1, LOOK_TIER)   → y = (RING_HEIGHT[ring] + depthDrop) * LOOK_TIER + jitter
取景：ringPath(ring.radius, RING_HEIGHT[ring]) → 层高原值，未乘 LOOK_TIER(1.3)，未算部门下沉
```

`LOOK_TIER` 默认 1.3。于是**取景的解析模型比真实场景矮 30%**，最下层（Agent 环）自然溢出。

| 视口 | 修前 zoom | 包围盒高 / 安全区高 | 越出安全区实体 | 最大越出 |
|---|---|---|---|---|
| 1440×1000 | 1.231 | 777 / 729（107%） | **19 个 Agent** | **35.1px** |
| 390×844 | 0.95 | 340 / 347（98%） | 0 | 0 |
| 320×720 | 0.55 | 164 / 175（94%） | 0 | 0 |

为什么既有门禁全绿也没发现：272 条军团检查里没有一条比对「实体位置」与「页面自己暴露的安全区」
（`[data-safe-bounds]`）。数据规模未变、无 pageerror、首屏时间正常、标签落地率正常。

## 2. 修法

```ts
// 每圈层高极值改由「绘制同一个函数」产出
const ringYExtent = new Map<number, { min: number; max: number }>();
for (const n of layout.nodes) {
  const y = nodeToVec3({ ...n }, 1, LOOK_TIER).y;
  // min / max 记录
}
// 取该圈 min、max 两条环轨迹的并集：
//   只取最低 → 顶部算矮；只取最高 → 底部算矮
```

不逐节点投影：`.504` 已证明逐节点投影依赖 yaw，会得到 113/115/121 三种 zoom；
而 `y` 只与 ring/depth 有关、与角度无关，所以「每圈最低/最高高度」是确定的。

## 3. 修后线上实测（`0.6.4-preview.557`）

| 视口 | zoom | 包围盒占安全区 | 越界实体 | 最大越出 |
|---|---|---|---|---|
| 1440 | 1.19 | 100–105% | 1–10 | 12.5–18.8px |
| 390 | 0.95 | 98% | 1 | 3.0–3.7px |
| 320 | 0.55 | 94% | 0 | 0 |

```

      但 1440 的 zoom 在同一构建、同一数据下出现 1.187 / 1.212 / 1.240 三个收束值（差 4.2%）。
```

## 4. 未消方差（残余第 10 条）

```
实测（收束后取样：连续 2s 不变且 writer 已知）：
  live .557 四次：1.212 / 1.240 / 1.187 / 1.187
  时间线探针三次：全程 1.187（12 秒不动）
⇒ 不是俯角问题：Agent 环投影长宽比三次都 0.930–0.934（俯角代理量几乎不变）
⇒ 形态像"两个不动点"：取景输入在某几次加载里比另几次"矮" 4%
```

已试并**已否决**的修法（`.558` 候选，未发布）：

```ts
// 入场结束（含降级中止）补一次收敛取景
fitPending.current = true;
```

否决理由：本地 dev 连跑 5 次确实变成同值（1.231，方差消失），
但该值让包围盒占安全区 **104%**（759 / 729），比线上 .557 的 1.187（101%）更差。
⇒ 「消除方差」和「取景更正确」两个目标没有同时达成，不能只满足其一就上线。

下一步方向（未实施）：把「入场所用编制签名」与「收敛取景所用签名」显式写进 DOM
（例如 `canvas.dataset.fitKey`），先证明是哪一次取景赢了，再改逻辑；
在拿到证据之前不再改取景代码。

### 取证过程中被自己否决的错误结论（留档）

1. 时间线探针第一版：25 次采样只成功 1 次，却从 1 个点输出了"不是陈旧取景"的判读。
   ⇒ 已加"覆盖率 < 60% 即判结论不可用"。
2. 延迟探针第一版：把 **所有** `/api/hub/*` 都延迟，采样时读到"0 节点 + 默认 zoom 1.120"，
   判读仍是"数据晚到不是原因"。
   ⇒ 已加三道门槛：只延迟指定端点、编制就绪（节点 >100）、样本有效（Agent >300 且已收束）。

## 7. `.558`：方差根因（两处）与线上复验

`.557` 之后遗留的 4% 收束方差，在 `.558` 里定位到两处具体缺陷并修复。

### 复现配方（无需改产品代码）

把图例数据 `/api/hub/session-status` 延迟 2500ms ⇒ 图例晚出现 ⇒ 取景执行时安全区还是 760px（稳定值 729）。
在 `.557` 上这条配方**必现** 1.240：

| 版本 | 收束 zoom | 内容包围盒 | 越界实体 | 最大越出 |
|---|---|---|---|---|
| `.557`（配方） | **1.240 / 1.240 / 1.187** | 764px | **10** | **18.2px** |
| `.558`（同一配方，线上实测 ×3） | **1.192 / 1.192 / 1.187** | 731–734px | 1 | 10.7–12.8px |

### 两处缺陷

```
① `fitPending` 是一次性事件：边界缩小的那一帧若取景被挡（入场 / 静默窗口），请求就丢了，
   之后没人再喊 ⇒ 画面永久停在按 760px 算出的 1.240。
   修法：新增「边界纪元」boundsEpoch —— measure() 判定边界变化就 +1；取景条件加上
        fittedEpoch !== boundsEpoch，且只有真的算出 fit 才记账。
        语义变成「取景必须用当前这份边界算过一次」，被挡不会丢。
② `.557` 的层高修复漏了回退分支：某圈暂无节点时仍回退成未乘 LOOK_TIER 的旧值，
   于是编制分批到达的瞬间，取景模型又缩水 2%。
   修法：回退值同样 ×LOOK_TIER，与绘制保持同一来源。
```

### 线上判据（`.558` / `7420f304`）

```
延迟图例 2500ms ×3：1.192 / 1.192 / 1.187，越界 1 个、最大 12.8px（安全区外还有 16px 间隙）
drift 三视口：19/19 PASS —— 1440 占安全区 101% · 390 97% · 320 94%
收敛方差（`.559` 复核 5 轮以上）：1.187–1.21（≤1.7%）—— 早前写"0.4%"是基于 3 次采样，样本更多后修正
health-all：13/13（`.560` 起新增目视抽检门） · 验收 20/20（legion 272/272）· CI 4/4 · 发布自检 4/4
```

### 取证纪律（本轮新增，都是被自己骗过换来的）

1. 一次采样不能下结论（时间线探针 25 次只成功 1 次，却输出了结论）
2. 固定 sleep 不能取样（3s 落在收束前的窗口，读到 1.24 就误判成"双稳态"）
3. 空场景不能判读（延迟所有 `/api/hub/*` ⇒ 0 节点 + 默认 zoom 1.120，仍输出了判读）
   ⇒ 现在探针有三道门槛：覆盖率 ≥60%、取景已收束、编制已就绪（节点 >100 / Agent >300）
4. 假设先用数据否证，再改代码：本轮 H1（俯角）、H2（数据晚到）都是先被数据否掉的

## 5. 判据与复跑

> 本仓库的 OSS 公开面检查会拦住任何写死个人家目录的路径（`/home/<user>/…`），
> 文档里的命令一律用环境变量或相对路径。

```
# 浏览器路径按本机 Playwright 安装位置给（不要写死某个人的家目录）
export PLAYWRIGHT_BROWSERS_PATH="${PLAYWRIGHT_BROWSERS_PATH:?先指向本机 ms-playwright 目录}"

node evidence/probes/legion-drift-clip.mjs https://dm.vansin.top            # 越界/裁切（收束后取样）
node evidence/probes/legion-fit-timeline.mjs https://dm.vansin.top 1440     # 取景时间线
node evidence/probes/legion-late-data-fit.mjs https://dm.vansin.top 2500 \
     DELAY_ONLY=/api/hub/session-status                                     # 复现配方：图例晚到
```

两条量法纪律（踩坑换来的）：

1. **分母用页面自己的安全区** `[data-safe-bounds]`，不是画布。
   画布含页头/工具栏：320 视口按画布算只有 28%，按安全区算是 94% —— 前者会把正常取景误判成"图小得离谱"。
2. **越界判据不是"必须为 0"**，而是"越出量 ≤ 16px"。
   页面 `measure()` 里 `y1 = header.y2 + 16`、`y2 = footer.y1 - 24`，16px 是最小的一侧间隙；
   部门盘是椭圆（ry≈18px），边缘擦边 3–13px 属模型可解释范围。
3. 取样必须等**取景收束**（连续 2s zoom 不变且 writer 已知），固定 sleep 会读到过渡值。

## 6. 教训

- 「门禁全绿」不等于「画面正确」：这条缺陷在 272 条检查 + 12 门基线里都是绿的。
- 探针自己也会骗人：时间线探针第一版 25 次采样只成功 1 次，结论却是从这 1 个点推出来的
  ⇒ 已加「覆盖率 < 60% 即判结论不可用」。
- 不要用"平均变好"当"修好了"：19 → 1 是事实，1.187 / 1.240 并存也是事实，两者都要写在报告里。
