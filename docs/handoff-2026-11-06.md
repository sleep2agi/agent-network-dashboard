## 二、性能：真正的根因不是"串行"

最初的判断是「请求太多被串行」，实测推翻：

- 单请求 TTFB 只有 82–275 ms（DNS 1–68ms、TCP 2–8ms、TLS 70–264ms）
- 但 `/api/hub/status` 响应体 **709,690 B**，且**未压缩**（`Accept-Encoding: identity` 与 `gzip` 下载字节数完全相同）
- 公网带宽约 240 KB/s → 单这一份 ≈3 秒；加 tasks 296KB、messages 315KB ≈6 秒，与首屏 6.7 秒吻合

**结论：先量「每个请求传了多少字节」，再谈请求数/缓存。**

## 六、一次失败的优化（ETag 条件请求），已整套撤回

- 服务端 ETag 成立（curl：200/245,620 B ↔ 304/0 B）

## 十、验证方法论：今晚新踩的两条（都导致过假结论）

### 10.1 重建后必须重启端口，再跑任何布局类探针

我在 **`npm run build` 之前启动的 3010** 上测布局，重建后 chunk 哈希变化导致 CSS 404，
页面「半裸奔」：`nav` 的 `display:flex` / `overflow-x:auto` 全部失效，
于是量出「390 下溢出 34/29/42px」。重启后同一页面 `scrollWidth = 390`（无溢出）。

**规矩**：`next start` 的进程只认启动时那份产物。重建 → 重启 → 再测。
凡是「布局/样式」类数字，先确认三件事：端口进程启动时间 > 构建时间、CSS 200、`data-*` 属性符合预期。

### 10.2 钳制元素（`max-h-*`）不是「裁切」

摘要卡用 `max-h-10 overflow-hidden` **按设计只显示 2 行**。第一版巡检把它算成「内容被裁」，
在浅色×小字×紧凑组合里误报 8 处。

**规矩**：
- `clipped` 只统计**没有** `max-height` 的硬裁切元素
- 钳制元素单独用 `clampBad` 验证：`clientHeight` 是否等于「整数行 × lineHeight」（偏差 >2px 才算异常）

第二条尤其重要：`.394` 上线时我说「没有被裁掉的字」，其实只量了节点行高，
漏了行内的摘要卡——**钳制高度没跟着字号缩放**，特大档下 52px 内容塞进 40px，从行中间被切。
这就是 `.397` 的由来。

## 十一、目前仍然开放的两件事

## 十二、共享机上的时间类断言：该判「inconclusive」，不该判「红」

`.398` 收尾时连跑三次军团套件，全都没过，但**每次红的项都不同**：

| 次 | 起始 load1 | 结束 load1 | 失败项 |
|---|---|---|---|
| 1 | 12.28 | — | 导航断言（URL 5s 内变 `/org`） |
| 2 | 20.63 | — | `perf:denseMedianFrame` |
| 3 | 7.66 | **19.82** | `perf:denseMedianFrame` + `tour:yawSettlesWithin500ms` |

三次全是时间/帧率类，且 `.398` 的 diff 只碰设置页登录设备卡片（与 `/legion/3d` 零交集）。
同机还有三个 `bun` 进程在 65–100% CPU 上跑（其他节点的构建/测试）。

**结论**：在这台机器上，「红」与「机器忙」目前无法区分。正确做法不是放宽阈值，而是：

1. 断言记录**测量时刻的 `load1`**；
2. `load1` 超过经验阈值（如 > 8）时，结果标 `inconclusive` 并**自动重采样**，最多 N 次；
3. 发布门槛写死：**必须存在一次全绿运行，且该次测量期间 `load1 < 8`**；`inconclusive` 不算通过；
4. 若长时间拿不到安静窗口，由人决定「继续等」还是「接受行为断言绿 + 时间断言 inconclusive」——决定要写进发布记录。

反面做法（今晚我明确没做的）：放宽帧率阈值、加长超时、拿上一版的结果给新版背书。

# 附二：2026-11-07 的方法论（比版本本身更值得带走）

## 十六、串联验收有盲区：第一套红，后面十几套根本没跑

`run-<N>-final-acceptance.py` 是**串联**的：第一个失败套件之后直接中止。
`.398`/`.399` 都栽在 legion（第 5 个），于是**后面 15 套从未运行**。

我一度把 `.397` 的「20 套全绿」当成 `.398/.399` 的数字往外报——这是错的，已更正。
**做法**：需要局部证据时，用每个套件自己的 runner 单独跑（`deploy/run-*-acceptance.py --label <suite>-<N>`），
19 套可以在 legion 未通过的情况下拿到完整证据。

## 十七、源码级验证 ≠ 产物级验证

线上跑的是 `releases/preview.<N>-<sha>` 里的构建产物，不是工作区源码。CSS 会被打包、chunk 会拆分。
**做法**：修复必须在**发布产物**上再验一遍（本文档中 `.399` 的设备列表修复与角标行高都做了产物级验证）。

## 十八、对照实验必须同数据量、同负载、交替轮换

我曾用「候选版本连模拟 Hub（1 节点）」对比「生产连真实 Hub（393 节点）」，
得出「候选快 4 倍」的错误结论。正确做法：

- 交替轮换多轮（A→B→A→B），各自记录 `load1`

实测结果（354 节点）：生产 `.397` 66.7 / 50.1 ms，候选 `.399` 66.7 / 66.6 ms —— 无回归。

## 二十、时间类断言在共享机上的判定协议（已有正文第十二节，此处补实测）

- 空白页基线：load 8.58 时 `about:blank` 仍为 16.7ms（60fps）→ 浏览器没有被全局限帧；

## 二十一、军团 3D 构图量化与叠压收敛（2026-11-07）

### 为什么要量化
「3D 不够震撼」是不可验收的说法。拆成可数的三个指标后，改动能被证明有效或无效：

| 指标 | 定义 | 工具 |
|---|---|---|
| `agentOverlapPairs` | 两个 Agent 椭圆中心距 < 0.85×(r₁+r₂) 的对数 | `layout-metrics.mjs` |
| `centerVoidRatio` | 画布中心 30% 半径内没有节点的采样比例（**必须含部门盘**） | 同上 |
| `deptCoverRatio` | 部门盘被 Agent 覆盖的面积比 | 同上 |

前置条件：`/legion/3d?debug=1` 会每 12 帧把投影结果写到 `window.__legionProjected`
（`{id,kind,label,depth,wr,ang,x,y,rx,ry}`）。只读导出，不参与渲染，不带 `debug=1` 时零成本。

### 实测结论（331 Agent / 1440 / 真实网络）
- 相邻 Agent 的屏幕间距中位 **9.5px**，而当时头像直径 **12.4px** → 必然叠压；
- 世界半径每 0.028 的间距，投到屏幕上只有 **8px**（世界→屏幕约 285px/单位）；
- 叠压集中在**左右两侧**（顶部 0 / 两侧 109 / 底部 27）——投影把 y 压扁约 30%，
  按世界角度均分会让两侧的点在屏幕上挤在一起。

### 参数扫描（每一步都量过，作废方案同样留档）
| 配置 | 头像半径 | 叠压对数 | 结论 |
|---|---|---|---|
| 3 档 + 等角均分（.399） | 6.2px | 125 | 基线 |
| 6 档 | 6.2px | 132 | 作废：世界 0.028 的间距只剩 8px，加档等于切得更密 |
| 3 档 + 投影弧长均分 | 6.2px | 124 | 作废：只解决角向，没解决「头像大于间距」 |
| 3 档 + 弧长均分 + 头像收缩 0.78 | 4.8px | 63 | 有效 |
| 4 档 0.84→1.00 + 收缩 | 4.8px | 49 | 但内层压在**人环 0.84** 上，弃 |
| 4 档 0.88→1.00 | 4.8px | 74 | 径向只 0.04（≈11px），挤回去 |
| **4 档 0.86→1.04** | 4.6px | **34** | **采用**（径向 0.06 ≈ 17px） |

### 两条必须记住的边界
1. **稀疏场景（<80 个 Agent）必须走原来的等角均分**。弧长均分会挪开最左/最右的点，
   演示态包围盒改由不对称的部门盘决定 → `present:stillCentred` 实测 70px（判据 60px）。
   套件夹具正是稀疏规模，所以这条不是「迁就测试」，是两种规模本就该用两种排布。
2. 剩余 34 对里多数是**跨档**、集中在投影深度轴上（相机接近侧视时不同半径几乎投到同一点）。
   加档、缩半径都压不下去（5 档实测 52 对）。要彻底消除需要按深度轴做屏幕空间排布，目前未做。

⇒ 临界点在 **load 10.67 与 11.92 之间（约 11）**，不是原先估计的 13。判定规则应先取重试数据再看负载：
`retriedMedian ≤ 16.7ms` 通过；`retriedMedian = 33.3ms` 且 `load1 > 13` 视为**环境受限**而非回归，
上报时必须同时给出 `median / retried / retriedMedian / load1` 四个数，缺一个就无法与他人结果比较。

**教训（第 29 条）**：我此前在 load 9.64 拿到一次 33.3ms，就写下「与负载无关，是 headless 软件光栅的渲染开销」。
这次的 269/269 直接推翻它——**那是用一个样本做的归纳**。正确表述只能是：

### 2. `?look=glow` 两次尝试都未达判据，已删除

| 版本 | 参数 | 中心亮度 | 外环亮度 | 中心/外环比 | 目标 |
|---|---|---|---|---|---|
| `.424` | haloAlpha ×1.8、半径 ×1.15 | 44.17 → 48.88（+10.7%） | 24.61 → 26.52（+7.8%） | 1.795 → 1.843（**+2.7%**） | ≥2.06 ❌ |
| `.425` | haloAlpha ×1.9、半径 ×**0.82** | 44.17 → **43.52（−1.5%）** | 23.32 → **24.61（+5.5%）** | 1.894 → **1.769（−6.6%）** | ≥2.06 ❌ |

两次都失败，且第二次更差：**收窄半径并不会让中心更亮，而是让光晕覆盖面积变小、中心反而变暗**。

**教训（第 30 条）**：「更亮」和「更聚焦」是两件不同的事，参数方向甚至相反。
只放大半径 → 内外一起亮（比值不动）；只收窄半径 → 覆盖变少、中心变暗（比值下降）。
在 2D 画布合成里，光晕亮度由 `alpha × 面积` 共同决定，单改半径等于同时改了面积与浓度，
**必须先算出面积变化再定 alpha**，否则就是盲调。这个变体因此删除，不再迭代。

## 三十九、细结构提亮：「两个口径」缺一个就会判错（2026-11-09 深夜）

做「连线提亮」时踩了一个方法论坑，值得单独记：**同一个改动，换个口径就能得出相反结论。**

用 `?look=nolinks`（只关连线）做画布差集，得到精确的「连线像素」集合（实测覆盖 **2.7%** 画布，
39,000 像素左右），再比同一批像素的亮度：

| 口径 | 定义 | α×1.6 | α×2.0 |
|---|---|---|---|
| `absRatio` | 连线区**绝对**平均亮度比 | ×1.10 | ×1.15 |
| `energyRatio` | 连线**自身光能**比 =（有连线−无连线）之比 | ×1.28 | **×1.44** |

为什么两者差这么多：连线区里大多数像素其实是节点与背景，0.8px 的线只覆盖像素的一部分，
所以「区域平均亮度」被稀释。**用 absRatio 判，任何细结构提亮都会被判死；**
**用 energyRatio 判，又可能放过「测得出但看不出」的改动。**

⇒ 判据必须是**双条件**：`energyRatio ≥ 1.3` **且** `absRatio ≥ 1.15`。
前者保证改动真实存在，后者保证用户真的能看出来。α×1.6 只过第一个（1.28/1.10），α×2.0 两个都过。

### 装置缺陷 9 条（今晚累计，全部可复现）
1. 参数写进每帧被重置的变量（glow 0.0%）
2. 探针选择器凭记忆写（`node-card-*` 不存在）
3. 列表条目是 `button`，不是 `<a>`
4. 行数用子元素 `top` 计数（同行 inline 被算成多行）
5. **模块入口路径凭记忆写**（sharp 是 `dist/`）—— 用 `createRequire` 走包解析
6. **`A && B && C &` 会把整条链后台化**（export PATH 失效 → node not found）
7. 持续重绘的画布用**元素截图**会等「稳定」而超时 → 用整页截图
8. **`nohup npx next start &` 的 `$!` 是 npx 包装，不是 next-server** → 端口不释放、
   旧进程读被替换的 `.next` 返回白屏，探针把白屏误读成「参数没生效」
9. 探针启动必须断言「canvas 存在 / 导出钩子存在」，否则 exit 2 —— 不允许产出 0 或 1.0 这种看起来正常的假值


## 四十、跨天发布：采集器与发布器的日期口径必须一致（2026-11-10 凌晨）

`.428` 的验收 23:52 开跑（`evidence/release-428-20261109/`），发布在 00:06 尝试——**跨天了**：

```
collect-428-main-ci.py: OUT = evidence/release-428-{当天日期}/main-ci.json  → 20261110/
publish-428.py:         OUT = sorted(glob('release-428-*'))[-1]            → 读最新目录
⇒ 采集器把 main-ci.json 写进一个只有 CI、没有验收产物的新目录
⇒ publish 报 FileNotFoundError，发布被拦
```
有意思的是：**`collect` 的注释里就写着「跨天时旧写法会让 check-release 找不到 JSON」**，
而 `publish` 已经改成 glob 最新目录——同一个坑只改了一半，于是以另一种形式复发。

处置：把采集器的输出目录也改成「取该 label 已存在的最新目录」（与 publish 同口径），
并把 `deploy/next-release.py` 的模板一并改掉，后续版本不会再撞。

**教训（第 35 条）**：修「跨天/跨目录」这类问题时，要找出**所有**依赖日期的地方一起改；
只修一侧，问题会从「找不到文件」变成「读到空目录」，更难查——因为报错位置离根因更远。

## 四十二、首屏基线终于量出来了：不是「内容出不来」，是「内容出来后查数据要 2 秒」（2026-11-10 凌晨）

工具：`deploy/perf/first-paint.mjs`（10 轮 / 6 轮，页面内采集，避免 CDP 往返误差）。

### 基线（`/nodes`，1440，load 9.3–10.4）
| 指标 | 中位 | p10 | p90 |
|---|---|---|---|
| `fcp`（首内容绘制） | **286ms** | 240 | 352 |
| `firstRow`（第一行节点出现） | **2320ms** | 2052 | 3380 |
| `ltMax`（最长长任务） | ~950ms | 827 | 977 |
| `ltTotal`（长任务总量） | ~1.6s | 1.27 | 1.98 |

极差比（firstRow max/min）**1.67** —— 比之前记录的「2–4 倍」小，说明在 load≈10 时中位数已经可用。

### 这组数字推翻了两个假设
1. **「首屏慢是因为内容出不来」** —— 错。`fcp` 只有 286ms，骨架/外壳很快就有了。
2. **「SSR 收益存疑，瓶颈在水合长任务」** —— 也不完全对。真正的 2 秒差距在
   **`fcp`(286ms) → `firstRow`(2320ms) 之间**：外壳已出，节点行还没来，说明在等
   `/api/hub/nodes` 的客户端请求 + 水合后才渲染。
   ⇒ SSR 如果把数据在服务端取好、直接吐出行内容，`firstRow` 有机会从 2.3s 掉到接近 `fcp`。

### SSR 的判据（写死，避免事后找说法）
```
同一负载区间（load 9–11）下：
  firstRow 中位 ≤ 1160ms（相对 2320ms 改善 ≥50%）
  且 fcp 中位不恶化超过 20%（≤345ms）
  且 ltTotal 不明显增加（≤2.0s）
```

### 装置教训（今晚第 13 条）
`firstRow` 前两版全为 null：先写死了 `button[data-node-list-item]`（桌面不是 `button`），
后又用 `MutationObserver`（条目可能在挂观察者前就存在）。
最终用 **50ms 轮询** 才拿到数——误差 50ms 对秒级指标完全够用。
**结论：观测方式要按「数据出现时机」选，不是按「哪个更优雅」选。**


## 四十三、首屏那 2 秒不在网络：数据 476ms 就到了，行却要 2.4s 才出现（2026-11-10 凌晨）

把「接口完成时刻」和「第一行出现时刻」放在同一条时间轴上（2 轮，1440）：

| 轮次 | firstRow | 数据接口 | 该屏最慢的 API |
|---|---|---|---|
| 1 | **2424ms** | `/api/hub/status?lite=1` @ **476ms** | stats 722 / tasks 499 / health 473 |
| 2 | **3086ms** | overview @ **495ms** | health 467 / stats 461 / task-stats 296 |

两个关键事实：
1. **`/api/hub/nodes` 根本没被请求**——`/nodes` 页用的是 `/api/hub/status?lite=1`（lite 投影里带 sessions）。
2. **所有 API 都在 722ms 内完成**，但第一行到 2.4–3.1s 才出现 ⇒ **数据到达后又等了约 1.9 秒**。

这 1.9 秒对得上「水合长任务总量 ≈1.6s」：列表是客户端组件（`useEffect` 取数 → setState → 渲染），
而水合把主线程占住，列表要等 React 接管后才画出来。

### 于是修法明确了（不再是猜）
| 做法 | 预期 | 备注 |
|---|---|---|
| **把列表做成服务端渲染**（服务端取 `status?lite=1`，行内容随 HTML 一起下发） | firstRow ≈ fcp（~300ms） | 对症：绕开水合等待 |
| 或「瘦水合」（把列表页依赖的大组件延后/拆包） | 可能降到 1.2–1.5s | 只能减轻，不能根治 |

⇒ 判据仍是第四十二节那组：`firstRow 中位 ≤1160ms`、`fcp ≤345ms`、`ltTotal ≤2.0s`。

**教训（第 37 条）**：「接口慢」和「渲染晚」在首屏指标上长得一模一样（都是 2 秒多）。
必须把 **API responseEnd 与 DOM 出现时刻** 放在同一时间轴上，才能选对修法——
否则很容易去做「接口瘦身」，而真正花掉时间的是水合后的渲染等待。


## 四十四、首屏 SSR 的第一版实施计划（2026-11-10 待做，未动工）

代码现状（已核对）：
```
app/nodes/page.tsx      → 'use client' + <NodesView />
app/nodes/NodesView.tsx → 'use client'，数据来自 useSessions/useHealth（SWR，客户端取数）
```

⇒ 首帧 HTML 里没有行内容，行要等 SWR 拿到数据 + 水合后才画出来（实测 2.4–3.1s）。

### 第一版只做一件事：把「行数据」提前到服务端
1. `app/nodes/page.tsx` 改成 **async Server Component**：服务端取 `status?lite=1`（沿用当前接口与 lite 投影，
   不新增接口、不改字段），把 sessions 作为 `initialSessions` 传给 `NodesView`。
2. `NodesView` 用 `<SWRConfig fallback={{ '/api/hub/status?lite=1': initialSessions }}>` 包住，
   让 `useSessions` 首帧就有数据；水合后 SWR 照常刷新（不改变最终一致性）。
3. 不改交互、不改布局、不新增 API。

### 风险与对策
| 风险 | 对策 |
|---|---|
| 服务端取数拿不到用户会话（cookie） | 服务端用 `cookies()` 转发；失败则回退到「无 fallback」= 当前行为，绝不白屏 |
| 水合不一致（HTML 与客户端首屏不同） | 只注入「服务端与客户端都会拿到的同一份 lite 数据」；不一致时以客户端为准 |
| 首屏体积变大 | 只注入列表所需的 lite 字段（已是 63KB 级） |

### 判据（沿用第四十二/四十三节）
```
firstRow 中位 ≤1160ms（基线 2320ms，改善 ≥50%）
fcp 中位 ≤345ms（不恶化 >20%）
ltTotal ≤2.0s
同一负载区间（load 9–11）
```


### 四十四·补充：这个计划有个硬阻塞（2026-11-10 凌晨，动手前发现）

继续核代码后发现第一版计划**不能直接做**：

```
network-context.tsx: networkId 只存在 sessionStorage（客户端）——服务器读不到
NodesView.tsx:      列表不做任何按网络的客户端过滤，完全依赖 API 的 network_id 过滤
⇒ 服务端如果把「全部网络」的会话注入 HTML，首屏会短暂显示别的网络的节点
   （比慢更糟：内容错）
```

三条可选路径：
| 路径 | 代价 | 是否解决 2 秒 |
|---|---|---|
| A. 把「当前网络」持久化到 cookie，服务端按它过滤后注入 | 需改选择网络逻辑 + 迁移默认值 | ✅ 且无错内容风险 |
| B. SSR 全部会话、客户端按网络过滤 | 需要新增客户端过滤（行为变更，还要处理 _hint 计数） | ✅ 但改动更大 |
| C. 不动数据，只瘦水合（拆包/延后重组件） | 改动最小，不碰数据语义 | 只能减轻（1.9s → 预计 1.0–1.4s） |

**结论**：先做 C（无数据语义风险），同时把 A 作为下一版的结构性改进。
不改「先做一版 SSR 看看」的赌法——那会把「显示别的网络的节点」这种错误带到线上。


## 四十五、`?look=light` 只在桌面成立，手机上不达标（2026-11-10 凌晨）

补测 390（线上 `.428`，同一判据）：

| 视口 | 连线像素覆盖 | 连线自身光能 | 连线区绝对亮度 | 判据 |
|---|---|---|---|---|
| 1440 | 2.67% | **×1.519** | **×1.175** | ✅ 双条件通过 |
| **390** | **5.64%** | ×1.184 | ×1.074 | ❌ 未通过 |

同一个 `LINK_BOOST = 2`，桌面达标、手机只有 ×1.18。原因不在参数，而在**画面构成不同**：
手机上节点更小、连线在画面里占比更高（5.64% vs 2.67%），连线区已经叠了大量节点与标签，
再提亮连线对「该区域平均亮度」的贡献被稀释；同时手机上连线本来就画得更实（像素少、线更粗相对）。

⇒ 结论：**不能拿桌面数据去推手机的观感结论**。
若要让 `light` 成为默认，只能做成「仅 ≥640 宽生效」——但那等于承认手机上没有收益，
所以更稳妥的处置是：**保持为可选参数**，不设默认。

**教训（第 38 条）**：一个变体在两个视口上可能得到完全不同的结论。
「桌面达标」不能外推到手机，必须两端各测一次——这次差一点就按桌面数据把手机一起改了。

## 五十二、军团帧率的真相：这台机器是**软件光栅**，绝对帧率不能代表用户（2026-11-10 凌晨）

我一度准备把「线上大网络 median 50ms（20fps）」当成用户体感问题去做「低功耗模式」。
先查渲染后端，结果直接否掉了这个方向：

```json
{"renderer":"ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)",
 "vendor":"Google Inc. (Google)","cores":8,"dpr":1}
```

**SwiftShader = 纯 CPU 光栅**，没有 GPU 加速。于是三组数字必须这样理解：

| 场景 | 实测 | 说明 |
|---|---|---|
| 线上真实网络（363 节点），headless | median 50ms（20fps） | CPU 光栅下的绝对值，**不能外推到用户** |
| 套件 fixture（约 72 节点），headless | 16.7ms / 33.3ms 双峰 | 同一环境，受 CPU 竞争影响 → 这就是它「不稳定」的根源 |
| 真机（有 GPU） | 未测量 | 目前无法在本机测，不能声称 |

⇒ 结论：
1. **不要用 headless 的绝对帧率谈用户体验**，也不该据此做「低功耗模式」；
2. 套件里 `perf:denseMedianFrame` 的双峰（16.7 / 33.3）是 **CPU 竞争**导致，
   与我们改的代码无关 —— 这解释了 `.431` 在 load 9.78 也红、`.430` 在 11.79 反而零重试；
3. 该断言仍有用，但只能当**大回归探测**（例如变成 100ms+），不适合当「60fps 认证」。

**教训（第 48 条）**：在给出「性能不达标」的结论前，先确认测量环境的**渲染后端**。
软件光栅下的绝对帧率，跟「用户会不会卡」几乎无关；拿它去优化，等于给测试机写代码。

## 五十五、反复咬我的两个流程错误（2026-11-10 凌晨，代价可数）

一晚之内，有两类操作重复出现，每次都让我白跑一轮：

### ① 切分支会带走未提交改动
- 现象：在分支上改完未提交就 `git switch main`，改动跟到 main 工作树里；
  更糟的一次是 `git checkout --` 想清掉 main 上的残留，连分支上那份也一起丢了。
- 代价：调试用的 `data-debug-session` 属性被我这样丢掉一次，导致后面的定性探针读到 0 处命中。
- 防线：**改完立刻提交到分支**（哪怕信息是 wip），再切分支；丢弃前先 `git stash list`/`git diff` 确认丢掉的是哪一份。

### ② `A && B && C &` 会把整条链后台化
- 现象：`cd … && export PATH=… && … nohup npx next start … &` 里，`&` 的优先级低于 `&&`，
  于是 export 也进了后台，前台后续命令报 `node: command not found`。
- 代价：探针脚本根本没执行，日志里只有一行「node: command not found」。
- 防线：**export 单独一行**，只把真正要后台的**一条命令**加 `&`。

**教训（第 58–59 条）**：这两条都不是知识问题，是操作习惯问题；
它们不会让代码变坏，只会让我反复以为「测过了」。

## 61. /nodes 首屏流式渲染（.441）——「用户早看见」优先于「数据早到」

### 61.1 结论数字（同机、带网络 cookie、6 轮中位）

| 指标 | .440 线上 | 阻塞式 SSR | **流式 SSR（.441）** |
|---|---|---|---|
| `firstRow` | 2337ms | 1024ms | **497ms**（p10 384 / p90 935） |
| `fcp` | 166ms | 1076ms | **142ms** |
| `ltTotal` | 1351ms | 1592ms | **455ms** |
| 控制台 error | 0 | 1（React #418） | **0** |
| 首次请求数 | status ×1 / nodes ×1 | 同 | 同（第二发是 5s 定时刷新，现网也有） |

### 61.2 为什么最后是流式，不是阻塞 SSR

阻塞式（`await` 取数后整页下发）把行内容提前到 1024ms，但 TTFB 被拖到 ~1s，
`fcp` 从 166ms 恶化到 1076ms —— **用户先看一秒白屏**。判据里 fcp 不得恶化 >20%，
所以这一版按自己的判据就是不合格的。

改为 `<Suspense>` 包住取数：外壳 142ms 下发，行内容随流到达（497ms）。
**性能目标不是「数据早到」，而是「用户早看见」**；两者冲突时，先保外壳。

### 61.3 实现要点（三处，别乱改）

1. `app/nodes/page.tsx` 必须是 **async 服务端组件 + Suspense**

     （否则把「全部网络」的会话渲染成当前网络 = 显示错数据）
   - 取数失败一律退回客户端取数（今天的整页行为），绝不让首屏变白
2. lite 投影只能有一份：`app/lib/lite-status.ts`
   - 服务端与 `/api/hub/status?lite=1` 共用；契约测试 `tests/lite-status-projection.test.mjs`
     已改为读这个文件，并把 5 个能力旗列入必需字段
3. Suspense fallback 必须是**零 Hook 静态骨架**（`app/nodes/NodesSkeleton.tsx`）
   - 直接拿 `<NodesView/>` 当 fallback 会让首屏多打 status/nodes 各一次（实测 ×2）

## 62. 规则文件写入冲突检测（.442）与技能复制（.443）

### 62.1 为什么写入还需要第四道保险

`.438` 的写入已有三保险：覆盖确认 / 写后重读 / 原样幂等校验。缺的是**并发**：

```
A 打开对话框 → 编辑中
B（另一个 Agent 或人）在这段时间改了同一个文件
A 点保存 → 三保险全部通过（写入成功、重读一致），但把 B 的修改**静默覆盖**了
```

规则文件是节点真在用的资产，这种覆盖必须显式让人确认。

### 62.2 实现（前端一层，不动 Hub 合同）

```
进入编辑 → 记基线 baseline = 当前内容
点保存   → 先重读一次（按钮显示「检查中…」）
  · 一致，或读取失败 → 走原有覆盖确认（读能力可能弱于写能力，读失败不能阻断保存）
  · 不一致          → 冲突条，三选一：
       ① 放弃我的改动，载入最新（draft ← 最新，baseline 同步）
       ② 保留我的改动继续编辑（关掉条，不动文件）
       ③ 仍然用我的版本覆盖（进原覆盖确认，再写）
写成功 → baseline = 刚写入的内容（否则自己写完后会立刻被自己判成冲突）
差异摘要只给行数：节点侧新增/改动 N 行 · 你独有 M 行 · 共 K 行
```

### 62.3 验收（探针用网络桩，不碰真实节点文件）

`evidence/node-rules/conflict-probe.mjs` 把 `/api/nodes/tool` 打桩，三场景：

| 场景 | 判据 |
|---|---|
| A 无外部改动 | 保存 → **直接**进覆盖确认，**不得**出现冲突条（防误报） |
| B 外部改动 | 冲突条 + 摘要含正确行数 |
| C 载入最新 | 编辑框 == 节点最新内容；再保存 → 覆盖确认（证明 baseline 已同步） |

桌面 1440 与窄屏 390 均全过；`.442` 上线后又在**公网**跑了一遍同样三场景。

## 63. 军团 3D 观感变体（.444）：`?depth=` 与 `?links=`

### 63.0 原则（沿用 .431 的教训）

```
观感改动先做成 URL 变体、先测量再决定默认；不用「我觉得更酷」当理由。
默认值必须等价于现状（depth=1 / links=1），否则等于偷偷改产品。
参数是否生效必须可被独立核验（曾经踩过 ?look=glow「参数写进去了但画布没变，比值 0.0%」）。
```

### 63.1 `?links=`：连线密度（两端达标）

```
做法：leaf 边按确定性哈希抽样（djb2(from|to) % 1000 < ratio*1000）
      父子部门主干边永不被抽 —— 层级骨架不能动
不用随机数：同一张图每次必抽同一批，否则刷新后拓扑变样会被当成「网络在抖」
```

两端实测（`deploy/legion-metrics/links.mjs`，读 `canvas.dataset.edges = "主干/叶子"`）：

| 档位 | 主干 | 叶子 | 叶子保留率 |
|---|---|---|---|
| 全量 | 14 | 348 | 100% |
| `?links=0.6` | 14 | 223 | 64.1%（期望 60±15） |
| `?links=0.4` | 14 | 151 | 43.4%（期望 40±15） |

结论：达标，可放心作为选项提供（默认仍为全量）。

### 63.2 `?depth=`：景深 / 透视强度（仅桌面达标）

```
做法：相机 dist 与 focal 同比例反向缩放（dolly-zoom）
      ⇒ 画面尺寸几乎不变，近大远小的落差变大
指标：投影尺度 p90/p10，尺度取 rx/wr（rx=投影像素半径，wr=世界半径，避免把「大部门本来就大」误判成「近处更大」）
```

| 视口 | 默认 | `?depth=1.5` | `?depth=2.0` | `?depth=3.0` |
|---|---|---|---|---|
| 1440 | 1.382 | ×1.07 | **×1.13** | ×1.24（形变风险） |
| 390 | 1.37 | ×1.01 | ×1.06（不足） | — |

副作用检查（1440）：叠压对数 23 → 22（未增）、画面高度 672 → 673（未缩）。

```
结论：桌面推荐 2.0；窄屏开到 2.0 也只有 ×1.06，不建议
取值域 0.4–2.2（3.0 不进上线范围）；**默认不开启**，等产品/设计判断
```

**手机为什么不达标（根因，写下来避免重复试错）**：窄屏的 focal 本身就按 2.4 系数放大、
相机距离相对场景纵深更远，同比例缩放的相对影响被稀释。
要手机也有纵深，正确做法是改**布局的 z 展开**或**相机距离量级**，而不是继续加大这个系数。

## 65. 3D 手机纵深：`?spread=`（z 展开）**实测否决**

### 65.1 动机

`.445` 让桌面默认有了景深，但手机没有（`?depth=2` 在 390 只有 ×1.06）。
相机系数这条路在窄屏到头了（§63.5），于是试第二条：**布局层拉 z**（`?spread=z 倍数`），
只动平面 z（前景更近、背景更远），不动 x/y，理论上不影响盘面大小与取景。

### 65.2 实测（同一探针，两端）

| 视口 | 默认 ratio / 叠压 | spread=1.6 | spread=2.0 |
|---|---|---|---|
| 1440 | 1.59 / 13 对 | ×1.14 · **17 对** | ×1.22 · **17 对** |
| 390 | 1.37 / 32 对 | ×1.06 · **49 对** | ×1.01 · **55 对** |

### 65.3 结论：否决，代码已回退

```
桌面：ratio 确实涨了（×1.14 / ×1.22），但叠压从 13 对涨到 17 对（+31%）
      —— 用遮挡换纵深，是把「看得清」换成「看着深」，不划算
手机：ratio 几乎不动（×1.06 / ×1.01，2.0 甚至回落到 ×1.01），
      而叠压从 32 对涨到 49/55 对（+53% / +72%）
      —— 两头都不成立，纯粹变糊
```

**为什么手机不行（根因）**：窄屏的 focal 本身按 2.4 系数放大、节点屏占比更大，
z 拉开后节点在投影上互相压得更紧；而透视缩放的变化量又被 focal 的缩放吃掉。
换句话说，手机的空间预算已经被「盘面 + 节点体量」占满，没有纵深的位置。

### 65.4 下一个候选（未做，等产品/设计定方向）

```
A. 提升「层次感」而不是「纵深」：强化层间高度差（tier 已 1.3）+ 层内排序规则
B. 光效：按层级分档的辉光预算与粒子流密度（纯装饰，可用截图差集判据，风险低）
C. 入场动效：分层依次点亮（有明确时间轴，可测「首帧到全亮」时长）
D. 视角：窄屏 pitch 已到 1.02 rad，继续加会让盘面更接近正圆但层间关系更平 —— 不建议
```

### 65.5 教训（第 68 条）：几何上的「拉深」与「不重叠」在手机上不可兼得

在固定视口里，纵深只能从「前后遮挡」里换。判断某个纵深参数是否可用，
不能只看 scaleRatio，必须同时看**叠压对数**——本轮 1440 的 ×1.22 看着漂亮，
但叠压 +31% 已经让它不合格。以后任何「拉 z / 改相机距离」的提案都按这两条一起判。

## 67. 3D 光效分档 `?glow=` —— **实测否决**（与 §65 同一判定逻辑）

### 67.1 动机

手机两条纵深路线都被否决（§63.5 相机系数、§65 布局 z 展开）。于是换一条
**不改几何**的杠杆：放大「主干泛光预算 + 两档辉光强度」（`?glow=`，默认 1，上限 2.5），
预期是「不改布局、不改命中、还能提升层次辨识」。

### 67.2 实现与可核验

```

bloom alpha = min(1, base * LOOK_GLOW)             // 0.055/0.035 与 0.15/0.09 两档
canvas.dataset.variant = "depth=…,links=…,glow=…"  // 参数必须可核验
```

### 67.3 实测（像素差集，复用 link-light 的 sharp 口径）

| 视口 | 取值 | 连线自身光能比 (C−B)/(A−B) | 参考：区域绝对亮度比 |
|---|---|---|---|
| 1440 | glow=2 | ×1.134 | ×1.051 |
| 1440 | glow=2.5 | ×1.19 | ×1.072 |
| 390 | glow=2 | ×1.114 | ×1.045 |
| 390 | glow=2.5 | ×1.03 | ×1.012 |

判据在测量前就写死：能量比 ≥1.2。**两端都不过**（1440 最好也只到 1.19，390 只到 1.03）。

```

而它叠在原本就亮的节点/连线区上，能量提升被稀释
绝对亮度比（×1.05–1.07）再次证明：看绝对亮度会低估/高估，必须以能量比为准
```

辉光 alpha 的物理上限（≤1）与底色亮度决定了它能带来的能量比上限；
在深底 + 已亮连线的场景里，这条上限大约就是 ×1.2。
**做之前先估上限**：如果上限也过不了判据，就不该花时间实现它。

## 68. 权限模式可写（.447）：用户令牌边界与「三态收敛」状态机

### 68.1 合同（来自 Hub 侧已存在的 REST 端点，非本仓库自造）

```
PUT /api/nodes/:id/permission-mode
  body {"mode": "normal" | "readonly" | "restricted"}
  成功 → {ok: true, permission_mode, previous}
  授权：用户令牌 + 节点主人 / 网络 owner·admin / Hub 管理员
        **节点令牌会被拒（403 user_token_required）**——作用于用户账号的端点不接受节点令牌
```

Dashboard 代理 `app/api/hub/nodes/[ref]/permission-mode`：
- 请求白名单：只转发 `{ mode }`；服务端二次校验取值（非法 400，不落 Hub）
- **响应白名单**：只回 `{ ok, permission_mode, previous }` + 可读 message
  （「白名单只做一半」等于没做：整包透传会让 Hub 将来新增字段直接落到浏览器）
- 只透传会话里的用户令牌，不缓存、不落密钥

### 68.2 面板状态机：三态缺一都会挂死或误记功

评审逐轮发现的问题，最终收敛成三条出口：

| 观测结果 | 文案 | 说明 |
|---|---|---|
| `permObserved === pending.mode` | 「已生效：X」 | 我提交的值生效了 |
| `permObserved !== observed0` 但不是我的值 | 「已被其他改动覆盖为「X」（请刷新核对）」 | **不替别人的动作记功**（归因转借） |
| 15s 内 `permObserved === observed0` | 「未确认：界面未收到新值，请刷新重试」 | 「不确定」必须能显示出来 |

实现要点：
- `pending = { mode, observed0 }`；清除判据是「**观测值变了**」而不是「等于目标值」，
  否则 Hub 归一化/新增取值时会永久挂着一个 Hub 并不处于的状态（比弹回更糟）
- 清理逻辑在 `useEffect([permObserved, pending])` 里，不在渲染期、不在 JSX IIFE 里 setState
- `if (permBusy) return` 挡在函数开头——键盘 Enter / 快速连选能绕过 `disabled`
- 网络层失败归一为「网络异常，请重试（权限模式未改变）」，与 Hub 拒绝分开
- 行结构抽 `InfoRowControl`（与 `InfoRow` 同 padding/gap/字号）；控件 `h-[var(--control-h)]`

### 68.3 验证边界（必须原样保留，别升级措辞）

```
已验证：非法 mode 本地 400（未落 Hub）；节点令牌调用被 Hub 403；回读状态未被写坏；
        viewer_can=false 时面板只读；状态机三态 + 归因 + 文案收敛（打桩 UI 探针）
未验证：真实用户令牌下的正向写入
        （正向证据需要「谁做的 / 什么时间 / 哪个节点 / 改前改后值」四项，缺一项不算）
```

### 68.4 教训（第 71 条）：状态机要按「观测值」收敛，不要按「期望值」收敛

按「等于目标值」收敛会有两个盲区：Hub 归一化取值（永远不相等 ⇒ 永久挂起）、
他人并发修改（值变了但不是你的 ⇒ 仍显示你的成功）。
**判据应是「世界有没有变化」，然后把变化归到三个互斥出口。**

### 68.5 教训（第 72 条）：能力判定要按「能力」分别做，不要「同源」

一度想用「能看到日志 ⇔ 能改权限」这一条同源规则，是过度约束：
两种能力绑在一起会造出新洞（有日志权限的人被迫获得改权限的可见入口）。
正确原则：**按能力分别判定 + 服务端强制**。

## 69. 运行日志面板（.448）：tail_node_logs 与「三态错误」

### 69.1 合同（Hub 侧既有能力，非本仓库自造）

## 70. 运行日志 / 项目文件夹 / 权限模式：三处「用户令牌 + Hub 授权」能力

### 70.1 三块的共同边界（写一次，三处复用）

```
凭据：会话里的 **用户令牌（V3 token）**，不是节点令牌
授权：Hub 侧判定「节点主人 / 网络 owner·admin」；节点令牌与旁观者在生成任何数据前被拒
可见性：能力旗（logs_capable / files_capable / viewer_can.permission_mode）
        × Hub 授权，两段都过才可能成功
不变量：能力按需分别判定，不做「同源」（能看日志 ≠ 能改权限）；
        代理只透传会话令牌，不降级、不缓存、不落密钥
```

### 70.2 三个代理的入参白名单（都在边界收敛）

| 工具 | 允许字段 | 额外守卫 |
|---|---|---|
| `tail_node_logs` | node_id/child_node_id/alias/network_id · lines(1..2000) · level(info\|warn\|error) · grep(≤200) · since_ts(数值) | — |
| `list_node_files` / `read_node_file` | 同上 + `path` | 只接受相对路径；拒绝绝对路径与 `..`；≤1024；非法直接 400，不发 Hub |
| `PUT /api/nodes/:ref/permission-mode` | 只转发 `{ mode }` | 服务端二次校验 normal\|readonly\|restricted；**响应也走白名单** `{ok, permission_mode, previous}` |

### 70.3 三处 UI 的共同纪律

```
· 错误三态：无权限（找管理员）/ 节点不可达（重试或查进程）/ Hub 报错（稍后再试）
· 能力缺失用中性色 + 「节点版本较旧，升级后可用」；红色只留给真正的读取失败
· 空态要分：无日志 vs 无匹配；空目录；无权限 vs 读不到
· 不能预览要说原因（二进制 / >256KiB / 疑似密钥），不假装能看
· 控件高度 --control-h；弹窗 760；只读面板不出现保存类按钮
```

### 70.4 教训（第 74 条）：桩的失效模式比产品更常见

`.448`/`.450` 两轮里，探针写错了 5 次（能力旗、请求发起方、⑥ 被自己的桩挡住、

## 72. 节点密钥名称（.452）：三层边界与「只读」的物理约束

### 72.1 为什么这块要单独写一节

同一个 Hub 端点既能读也能写密钥（`action: list | put | delete`）。代理一旦「顺手都转发」，
就会把「看名称」升级成「写密钥」。所以这一版的重点不是 UI，而是**把能力面裁到只剩读**。

```
① POST 代理：只放行 action:"list"；put / delete → 400，不转发
② GET  代理：响应白名单 { ok, status, error, revision, keys:[{key,source}] }
             ⇒ Hub 将来在 snapshot 里加 values 也不会流到浏览器
③ UI：只渲染 key 名 + source；副标题「仅名称，值不可读」+ 页脚「Hub 不返回密钥值」
```

### 72.2 合同（源码确认）

```
POST /api/nodes/:id/secrets?network_id=… {action:"list"} → {ok, request_id, status, expires_at}（120s 过期）
GET  /api/nodes/:id/secrets/:request_id                 → snapshot { revision, keys:[{key,source}] }
节点侧 project() 对 list 不返回 values
凭据：用户令牌；节点主人 / 网络 owner·admin
```

### 72.3 探针（两视口四条全过）

```
① 列表 2 个 key + revision 3 + 「仅名称，值不可读」
② 空态：该节点没有配置密钥
③ 错误三态：forbidden / unreachable（含 expired）/ hub-error
④ **action=put → 400（真实代理，未转发）** ← 这块的安全底线
```

### 72.4 教训（第 76 条）：断言放宽要放宽「措辞」，不能放宽「语义」

第一版探针要求页脚必须出现「值不可读」四个字，而实际页脚写的是「Hub 不返回密钥值」——
同一语义的另一种措辞。正确修法是允许同义表述（副标题或页脚任一成立），
**不是删掉这条断言**。判据的目标是「界面必须说明只返回名称」，不是「必须用某个词」。

## 73. 工具拒绝原因透传（.453）：拒绝在 payload 里，不在传输层

### 73.1 现象

真实数据验收（节点令牌）时，运行日志 / 项目文件夹 / 密钥名称三块都显示
「Hub 没有返回请求号」。看着像 Hub 没回数据，实际是 **Hub 回了拒绝**：

```
{ ok: false, error: "node_token_cannot_read_logs", message: "…use a user login" }
```

代理只看了传输层 HTTP ok，于是把 `ok:true` 原样返回给前端；
前端拿不到 `request_id`，只能报「Hub 没有返回请求号」——**真实原因被这句兜底文案盖掉了**。

### 73.2 修法

代理层一处判定，三个面板同时受益：

```
if (payload.ok === false) → { ok: false, kind: 'denied', error: message || error }
```

配合三面板 `classifyError` 扩展（匹配 `user login` / `登录` / `cannot` → 归「无权限」，
而不是笼统的「Hub 报错」）。

### 73.3 教训（第 77 条）：桩测不出「真实拒绝的形状」

桩里我编的是 `{ok:true, payload:{...}}` 和 `{ok:false, error}` 两种形状；
真实 Hub 的拒绝是**第三种**：`ok:false` 嵌在 payload 里。

```
桩能测「分类逻辑对不对」，测不出「Hub 真实契约长什么样」
⇒ 凡是「真实数据才暴露的文案问题」，都要有一条真数据复验，不能只靠桩全绿
```

## 74. 弹窗标题抽取 + 可访问名称（.454）：抽组件，不抽变量

### 74.1 为什么不抽 `--fs-title`

五个面板的标题各写一遍 `<div class="truncate text-[14px] text-[var(--fg)]">`。
最省事的做法是抽一个 `--fs-title` 变量，但那只解决「字号」：

- 截断策略（`truncate`）、别名 span 的间距与色、副标题的 testid 全都没有收口
- 下一次要改「标题 + 副标题」的关系时，仍然要改五处

所以抽的是**组件** `app/components/DialogTitle.tsx`（语义 `<h2 id>` + 可选副标题），
五个面板各减 6 行样板。

### 74.2 只接管标题块，不接管右侧按钮区

第一版设计让 `DialogTitle` 接管整行（含 `right` 槽），要把五个弹窗的按钮组搬进去。
判定不做：重排面越大，越容易在「看起来只是挪了几行」的改动里改坏交互。

```
只抽标题块 ⇒ 每个弹窗的 header 行与按钮保持原样
判据因此可测：相同标题串 5 → 1、text-[14px] 全仓 7 → 3、5 处 aria-labelledby
```

### 74.3 顺手修的可访问性问题

五个模态框此前只有 `aria-label`（且是中文硬串），没有语义标题，
屏幕阅读器打开时只念「对话框」。现在标题是 `<h2 id={useId()}>`，
容器 `aria-labelledby={titleId}`，读出来的是「运行日志 / 项目文件夹 / …」。

### 74.4 教训（第 78 条）：批量模板替换必须靠编译器收口

用脚本按固定模板替换五处时踩了三个坑：

```
① 标题本身已是 JSX 表达式 {t('…')} ⇒ 模板又包一层变成 {{…}}（tsc 报 TS1005）
② Files 的副标题是 JSX（面包屑按钮 + map）⇒ 必须包成 fragment，不能当表达式塞
③ Logs 的副标题是「文本 + 时间」两段 ⇒ 同样 fragment；Secrets 副标题内含 <span> ⇒ 亦然
④ 五个文件的 const titleId = useId() 首轮全没插进去（函数签名跨行，正则没命中）
```

四条全部由 `tsc --noEmit` 报出来。**批量改结构时，编译器就是唯一的验收人**；
「看着改完了」不算完成。

## 75. 日志面板「旧结果覆盖新结果」（.455）：共享 ref 当取消标志是反模式

### 75.1 现象

在日志关键字框里快速输入，列表会闪回上一次的内容；
切换错误原因后重新打开面板，有时看不到真实错误。

### 75.2 根因

```tsx
const cancelled = useRef(false);
useEffect(() => {
  cancelled.current = false;              // 每一轮开始都重置
  …await call(…)…
  if (cancelled.current) return;          // 读到的是「新一轮」的 false
  setPhase(…);                            // ⇒ 上一轮的迟到结果照样写回
  return () => { cancelled.current = true; };
}, [attempt, grep, level, lines, sinceMinutes]);
```

同一个布尔被所有轮次共享，下一轮一开始就把它重置成「未取消」，
于是**上一轮的请求返回时读到的永远是 false**——清理逻辑形同虚设。

### 75.3 修法

```tsx
const runIdRef = useRef(0);
useEffect(() => {
  const myRun = ++runIdRef.current;
  const alive = () => runIdRef.current === myRun;
  …await call(…)…
  if (!alive()) return;      // 迟到的旧请求一律丢弃
  return () => { if (timer) clearTimeout(timer); };
}, […]);
```

判据（同一探针，2 视口 × 3 轮 = 6 次）：修复前 3/6，修复后 **6/6**。

### 75.4 教训（第 79 条）：「偶发失败」先分清是产品缺陷还是测量缺陷

第 76 条说过「断言要放宽措辞不放宽语义」；这条是它的同胞：

```
探针 6 次挂 3 次，失败点在 ③ 和 ④ 之间漂移 ⇒ 第一判断是「有竞态」
拿到 DOM 现场才发现第二层：在场 testid 里有 node-logs-not-capable
⇒ 探针取样的是「列表第一个节点」，而列表随活跃度变化，旧节点不注册 logs 能力
⇒ 面板显示「该节点未上报能力」是正确的，探针却在等「无权限/超时/hub 错误」，空等 45s
```

所以两层都要修，且**层与层要分清**：

| 层 | 性质 | 处置 |
|---|---|---|
| 产品 | 旧结果覆盖新结果 | 改代码（runId 令牌） |
| 测量 | 取样节点不确定 | 改探针（按能力逐个试 + 打印取样节点） |

### 75.5 探针现在的取样规则（可复用）

```
① 优先本次测试节点（cfg.node_name）
② 列表里没有它就按顺序逐个试，直到某个节点真的上报 logs 能力
③ 每轮打印「取样节点：xxx」与「跳过 xxx：未上报 logs 能力 / 30s 无终态」
④ 全列表都没有有能力的节点 ⇒ 明确 FAIL，不静默退化
失败时打印在场所有 node-logs-* testid 与弹窗文案（判据不放宽，只加现场）
```

### 75.6 一天之内修掉的四个「测量缺陷」（都不是产品缺陷）

| # | 缺陷 | 表现 |
|---|---|---|
| 1 | 固定等 1200ms 再读文案 | ③ 偶发读到上一屏 |
| 2 | 终态白名单漏 `not-capable` | 旧节点下空等 45s |
| 3 | 取样节点取「列表第一个」 | 选中旧节点 → 误判成「分类失败」 |
| 4 | 窄屏列表虚拟化、点不到已枚举的条目 | 抛异常打断整轮 |

第 4 条修法是「点不到就当这条取样不可用，打印跳过原因并换下一个」，
不是放宽断言——**终态、文案、testid 三条判据一条没动**。

```
产品代码当天只发现两个真问题：拒绝原因被盖掉（§73）、旧结果覆盖新结果（§75）
其余四次失败全是测量层 ⇒ 报告时要把两类严格分开，不拿测试修复充产品进度
```

```
t=711…1586ms  zoom 恒为 1.120        ← 入场本该在这段里出现 0.69→1.12
t=2302ms  zoom 1.156（nodes=367，真实数据落定后的小幅取景调整）
min 1.120 / max 1.157
```

`deploy/legion-metrics/entrance.mjs` 同一现象：`zoomStart 1.217 → zoomEnd 1.157`（Δ-0.06）。

### 77.2 已排除与未排除

```
已排除：prefers-reduced-motion 的影响
  强制 reducedMotion: 'no-preference' 重测，曲线完全一致（仍恒为 1.120）
未排除：
  a) 首次 fit 发生在占位节点（nodes=1）上，intro 的目标 want 被 MAX_ZOOM 夹住，
     动画在采样开始前（<689ms）就结束了
  b) introDone 被「恢复本地视角 / 分享链接」分支提前置 true（page.tsx 约 515–525 行）
     导致 `!introDone.current` 块整段不执行
  c) 入场确实跑了，但 `__legionProjected.zoom` 暴露的是「取景后的目标值」而非当前值
     —— 那么测量装置需要暴露 `introRef` 在跑与否
```

### 77.3 结论（已定性，2026-11-10 收工前）

**入场是正常的，问题在测量装置。** 加了每帧只读探针后实测：

```
data-intro-state   idle → running → done
data-intro-applied 0.919 → 1.026 → 1.081 → 1.127 → 1.145 → 1.155 → 1.157   （t2 167ms → 950ms）
data-intro-from/to 0.731 / 1.180
entrance.mjs 复测：zoomStart 0.85 → zoomEnd 1.217（Δ+0.367）· 稳定 1652ms · 反向 0 · 单调
```

真因：`window.__legionProjected` **每 12 帧才导出一次**（page.tsx 约 1275 行），
900ms 的入场只采到 2 个点；`zoomStart` 落在入场中段，于是 Δ 被读成 -0.06。

### 77.4 修法与判据

```
① 页面：debug=1 时把入场状态机暴露到 canvas.dataset（state/from/to/applied/t）
   —— 只读探针，生产路径零影响（一次 if (debugProjRef.current)）
② 量具：deploy/legion-metrics/entrance.mjs 改为每帧读 data-intro-applied，
   读不到才回退到 __legionProjected.zoom
③ 判据（沿用）：Δzoom ≥ 0.20 · 稳定 ≤ 3200ms · 反向 0 次 · 单调
   ⇒ 现状已达标（Δ0.367 / 1652ms / 0 / true）
```

### 77.5 教训（第 81 条）：采样频率低于被测事件时长，等于没测

```
入场 900ms，导出周期 12 帧（约 400ms @30fps）⇒ 只有 2 个采样点
2 个点足够算「差」，但不足以确定「起点」——zoomStart 取到了动画中段，
于是「+43% 的推近」被读成「-6% 的抖动」

同类风险：任何「每 N 帧导出一次」的观测口径，都不能用来判断时长 < N 帧的事件
⇒ 要么把导出降到每帧（仅 debug），要么在事件内部埋一行真值
```

## 78. 军团 3D 入场「穿层」变体 `?intro=fly`（.456 变体 / **.457 起桌面默认**）

> **口径（别读错）**：默认已开（桌面 ≥768px）· **入场窗口 fps 已测：两版同环境都约 20fps，
> 属渲染环境与本机基线负载所致，非变体代价**（见 78.5）· 稳态帧率已测无系统性退化（78.5pre）。
> 也就是说：这版不是「测过性能才升默认」，而是「几何达标 + 变体无额外代价」才升的。

### 78.1 为什么是这个方向

§77 定性后确认：入场推镜本来就正常（0.62×→1.0×，Δ+0.43）。
于是「震撼」的下一步不能是「修入场」，而要在**视角层面**加东西：

```
纯缩放 = 观感「画面放大」      → 已有的部分
俯仰抬升 = 观感「换个观察位置再立起来」  → ?intro=fly 加的部分
```

相比被否过的两个方向（`?look=glow` 能量 ≤×1.19、`?spread` 遮挡 +72%），
俯仰变化不改变信息密度、不增加绘制量，失败也只是「没那么好看」，不会变丑。

### 78.2 实现

```ts
// 入场创建处
const pitchTo = view.pitch;
const pitchFrom = INTRO_MODE === 'fly' ? Math.max(-1.1, pitchTo - INTRO_PITCH_DELTA) : pitchTo;
view.pitch = pitchFrom;
introRef.current = { t0: now, from: want * 0.62, to: want, pitchFrom, pitchTo };
// 入场动画里（与缩放同一条 ease-out）
if (a.pitchFrom !== a.pitchTo) view.pitch = a.pitchFrom + (a.pitchTo - a.pitchFrom) * ease;
// 结束时显式落位，避免残留偏差
if (t >= 1) { view.zoom = a.to; view.pitch = a.pitchTo; introRef.current = null; }
```

默认仍是 `zoom`；`?intro=fly` 才启用；`prefers-reduced-motion` 时整段入场本来就不跑。

## 79. 三类「守卫失效」缺陷（评审方法论，2026-11-11 与通信设计师共同整理）

验收验的是**正常路径**；守卫只在**非正常路径**才有意义。
所以守卫类代码的评审方式要反过来：**不是「跑一遍看它对不对」，而是「找出它失效时会发生什么」**。

### 79.1 三类与各自修法（**修法不同，不能混用**）

| 类 | 成因 | 实例 | 正解 |
|---|---|---|---|
| ① 条件组合 | 机制正确，罕见状态同时出现才错 | 慢设备 + fit 恰好到点（.460 落点漂 20%）· 慢设备 + 900ms 内转屏（.461） | 读码 + 文档 + 只读探针；验收补不到 |
| ② 机制交互 | 两个各自正确的机制抢同一变量 | 入场动画 × fit 重取景（都在写 `view.zoom`） | **所有权窗口**：明确「谁在什么窗口内拥有该变量」（.460 的 900ms 静默） |
| ③ 同帧竞争 | 同一帧内先写后覆写；状态最终值是「最后一个写者」而代码意图是「第一个写者」 | .458 降级设终态后，下面 3 行插值当场覆盖回去 | **写后即停**（`return` 或二次条件），并在注释里写「为什么必须停」 |


### 86.3 对上一轮选项排序的修正

```
上一轮我给的是：① 条件引线 > ② 布局收紧 > ③ 第二通道 > ④ 脉冲
```


### 89.3 修订后的结论清单

```
已作废：② 布局收紧（评审已撤回；数据证明中心余量是唯一撑得住的余量）
已收窄：碰撞的病因是「同深度环上的跨父子部门角度冲突」，不是「盘整体过密」

```

```
  同深度、跨父 ⇒ 跨扇区无避让机制（本案）
```

## 94. 「一个资源 + 两个写者」：跨尺度的同一类缺陷（2026-11-11，`.483` 后）

> 结论来自评审（通信设计师）：同一类缺陷在时间尺度上放大后仍然是同一类。
> 帧级、秒级、分钟级、文件级，都是「一个资源 + 两个写者」；修法也一致：
> **所有权窗口 / 互斥 / 单一写者**。

### 94.1 今天的六个实例（按尺度排列）

| 尺度 | 资源 | 两个写者 | 处置 |
|---|---|---|---|
| 帧 | `view.zoom` | 入场动画 vs 降级覆盖 | `.460` 的 900ms 静默窗口 |
| 秒 | `view.zoom` | 入场动画 vs fit 重取景 | 同上（静默窗口） |
| 分钟（进程） | `.git/release-in-progress` | 两条发布链 | `.483` 后加的发布互斥守卫 |
| 分钟（进程） | 端口 3109 | 构建脚本 vs 测量脚本 | 串行化 + 测量前后断言服务版本不变 |
| 文件 | `releases/preview.NNN-*` | 同版本号两次生成 | 生成器拒绝覆盖已存在脚本 |
| 文件 | 工作树 | 人 vs 发布链 | 生成器要求干净树 |

```
⇒ 「静默窗口」与「互斥守卫」不是两种技巧，是同一条原理的两个尺度。
```

### 94.2 同源要逐个参数做，不是一个「同源」就全同源

今天修过三次「模型 ≠ 渲染器」，每次只是参数不同：

```
① 相机      ：relax 用 0.85，渲染用 1.02（窄屏）        → .472 单一来源 + 数值契约
② 屏幕投影  ：relax 用世界坐标距离，渲染看投影后距离      → .471 直接用 projectPoint
③ 层高      ：relax 用 tierBoost=1，渲染用 1.3（LOOK_TIER）→ .480 参数化 + 断言
```

### 94.3 同一语义在多个绘制通道里，只乘一次等于没乘

```
连线有三遍绘制：光晕（9px/4px）· 主描边 · 流光尾迹
.intro2 只给「主描边」乘了 reveal ⇒ 未出现的层，线在光晕那两遍里已经画亮
⇒ 视觉现象：p=0.10 时中枢到部门的线已全亮，而部门盘还没出现（「线连到空处」）
⇒ 修法：三遍共用一个 edgeRevealOf(e)，未出现的层直接不画
⇒ 证据：p=0.10 的非背景像素占比 8.21% → 7.52%（差值就是被去掉的空连线）
```

### 94.4 守卫本身也要被验证：它可能读到自己写的状态

```
第一次实现的发布互斥守卫放在 main() 里，而「写标记」在模块导入时执行
⇒ 守卫读到的永远是自己刚写的标记 ⇒ 它会永久拒绝一切发布（且看起来"在工作"）
⇒ 修法：守卫必须在「写标记之前」执行（代码里已注释这条顺序约束）
⇒ 自测两条路径缺一不可：
    A 标记 pid 存活 → 必须拒绝（exit 1 + 打印现有链信息）
    B 标记 pid 已死 → 必须打印「看过标记」+ 清理 + 继续
⇒ 教训：**守卫的日志必须能自证它看过标记**，否则退出码 0 会被误读成「没生效」
```

### 94.5 版本号纪律（补充 §93）

```
未部署的版本优先同号重建；同号重建产生两份目录时，判定依据是
  HEAD + ancestor（8c91bba5 是 41daecb2 的祖先 ⇒ 新的包含旧的），

```

## 95. 第四处同源点：背板尺寸与绘制变换（2026-11-11，`.483` 后）

> 相机（§94）、屏幕投影、层高之后，第四个「同源」点在**渲染管线内部**：
> 背板（canvas.width/height）与绘制变换（ctx.setTransform）必须乘同一个降档系数。

### 95.1 缺陷形态

```
applyResolution(scale)：canvas.width = size.width * dpr * scale      ← 背板缩小
主绘制：ctx.setTransform(dpr, 0, 0, dpr, 0, 0)                       ← 变换仍按满 dpr
⇒ 绘制坐标按满 dpr 展开，超出缩小后的背板 ⇒ 右侧/下侧被裁掉
⇒ 再由 CSS 把小背板放大回容器 ⇒ 用户看到「画面放大 1/scale 倍且缺一块」
实测（366 节点 / dpr2）：拖动中背板 1478×1080，绘制覆盖 2464×1800
```

### 95.2 这是存量缺陷，不是新功能引入

```
同一个 applyResolution 被「超大网络交互期降档」使用：
  interacting = huge (>250 节点) && now < interactingUntil.current (180ms)
  applyResolution(interacting ? RES_LOW(0.6 @dpr2 / 0.75) : 1)
⇒ 也就是：每一个 >250 节点的网络，**每次拖动**都会走这条错误路径
⇒ 只是它看起来像「拖动时画面跳动」，不像 bug，所以一直没被报上来
```

### 95.3 量法的第二次翻车：量具时窗 ≠ 被测时窗

```
第一次：mouse.move → wait 400ms → 读 canvas.width
        结果 2464/2464，ratio=1.0 ⇒ 差点得出「降档没生效」
        真相：交互窗口只有 180ms，等 400ms 读到的是"已恢复"的满分辨率
修法：拖动后 50ms 内取值；截图期间每 40ms 抖动一次鼠标，保证整段都在窗口内
验收：idle 2464×1800 · during 1478×1080 (ratio 0.600) · after 2464×1800 (restored=true)
```

### 95.4 否证记录：自适应降档开关 `?dynres=1` 不成立

```
假设：dpr2 掉到 11fps 是像素填充受限 ⇒ 降背板分辨率能救
实测（headless + SwiftShader，1440×900，同环境空白页恒 60fps）：
  dpr1 基线 31.0fps（1.30M px）
  dpr2 基线 11.3fps（5.18M px）
  dpr2 + 背板降到 0.58（1.49M px）⇒ 13.5fps（仅 1.19×）
  720×450（0.32M px）⇒ 53.7fps
⇒ 面积降 71% 只换来 19% 帧率 ⇒ 该机器开销**非像素填充主导**（逐节点/逐边绘制调用为主）
⇒ 处置：开关按前置判据丢弃（判据 ≥18fps），只保留变换同源修复；
  不把「默认关的无效开关」留在代码里充当产出
```
```
附带结论（可用于未来判断）：A/B 两案在 1440 与 390 下均无帧代价
（三变体 fps 差 ≤0.5，p50/p99 同档）⇒ 「设为默认」在流畅度上没有反对意见
```

### 95.5 断言

```
tests/legion-backbuffer-transform.test.mjs
① 背板 = size.width * dpr * scale
② 主绘制变换 = dpr * resScale
③ 禁止再出现写死的 setTransform(dpr, 0, 0, dpr, 0, 0)
⇒ 同源关系一旦被拆开，CI 先红；不依赖人记得
```

```
## 97. 视觉中性回归：`.483` vs `.484` 同尺 A/B（2026-11-11）

> 修复把 `setTransform(dpr)` 改成 `setTransform(dpr * resScale)`。
> resScale=1 时数学等价，但"数学等价"不等于"像素等价"，所以要用同一把尺子量两个版本。

### 97.1 方法与口径

```
不截图：截图含侧栏/顶栏，且需要 PNG 解码依赖；被这次修复影响的是**画布像素**。
直接读 canvas 的 device pixels：
  · 背景 = 四角均值；非背景 = 与背景差值 > 阈值
  · deviceScaleFactor=1，1440×900，`?intro2=1&intro2freeze=<p>` 冻结入场进度
  · 同一脚本跑 `.483`（releases/preview.483-41daecb 起在 3301）与 `.484`（生产 3001）
```

### 97.2 指标必须先标定：d24 会饱和

```
阈值 24：两版四帧全部 = 58.18% ⇒ 深空渐变本身就被算作"非背景"，指标饱和、无分辨力
阈值 60：两版四帧 14.5 → 15.1 → 15.4 → 19.5（随 p 递增，与入场推进一致）
⇒ 教训：先确认指标能分辨差异，再用它证明"没有差异"；饱和的尺子说"一样"时什么都没说
```

### 97.3 噪声底（每版连跑 3 次，d60）

| 冻结 p | `.483` 三次 | `.484` 三次 | 版间差 | run-to-run 抖动 |
|---|---|---|---|---|
| 0.10 | 14.61 / 14.53 / 14.50 | 14.61 / 14.60 / 14.53 | 0.00 | 0.11 |
| 0.33 | 14.81 / 15.12 / 15.10 | 15.11 / 14.79 / 15.11 | 0.00 | 0.32 |
| 0.60 | 15.30 / 15.37 / 15.41 | 15.36 / 15.58 / 15.23 | −0.05 | 0.35 |
| 1.00 | 19.41 / 19.57 / 20.27 | 19.40 / 19.58 / 20.27 | +0.00 | 0.87 |

```
⇒ 版间差（均值）全部 ≤ 0.05pp，而同一版本重复测量的抖动是 0.11–0.87pp
⇒ 结论：在可测精度内**测不出两版差异** ⇒ 该修复对画面是视觉中性的
⇒ p=1.00 抖动最大（0.87）：外环流光/数据包相位每次不同，属场景动画噪声，不是版本差异
