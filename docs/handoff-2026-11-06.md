## 二、性能：真正的根因不是"串行"

最初的判断是「请求太多被串行」，实测推翻：

- 单请求 TTFB 只有 82–275 ms（DNS 1–68ms、TCP 2–8ms、TLS 70–264ms）
- 但 `/api/hub/status` 响应体 **709,690 B**，且**未压缩**（`Accept-Encoding: identity` 与 `gzip` 下载字节数完全相同）
- 公网带宽约 240 KB/s → 单这一份 ≈3 秒；加 tasks 296KB、messages 315KB ≈6 秒，与首屏 6.7 秒吻合

**结论：先量「每个请求传了多少字节」，再谈请求数/缓存。**

## 六、一次失败的优化（ETag 条件请求），已整套撤回

设想：首页 5 秒轮询 247 KB，内容多半没变 → 304 可省 178 MB/小时。

- 服务端 ETag 成立（curl：200/245,620 B ↔ 304/0 B）

## 十、验证方法论：今晚新踩的两条（都导致过假结论）

### 10.1 重建后必须重启端口，再跑任何布局类探针

我在 **`npm run build` 之前启动的 3010** 上测布局，重建后 chunk 哈希变化导致 CSS 404，
页面「半裸奔」：`nav` 的 `display:flex` / `overflow-x:auto` 全部失效，
于是量出「390 下溢出 34/29/42px」。重启后同一页面 `scrollWidth = 390`（无溢出）。

**规矩**：`next start` 的进程只认启动时那份产物。重建 → 重启 → 再测。
凡是「布局/样式」类数字，先确认三件事：端口进程启动时间 > 构建时间、CSS 200、`data-*` 属性符合预期。

### 10.2 钳制元素（`max-h-*`）不是「裁切」

摘要卡用 `max-h-10 overflow-hidden` **按设计只显示 2 行**。第一版巡检把它算成「内容被裁」，
在浅色×小字×紧凑组合里误报 8 处。

**规矩**：
- `clipped` 只统计**没有** `max-height` 的硬裁切元素
- 钳制元素单独用 `clampBad` 验证：`clientHeight` 是否等于「整数行 × lineHeight」（偏差 >2px 才算异常）

第二条尤其重要：`.394` 上线时我说「没有被裁掉的字」，其实只量了节点行高，
漏了行内的摘要卡——**钳制高度没跟着字号缩放**，特大档下 52px 内容塞进 40px，从行中间被切。
这就是 `.397` 的由来。

## 十一、目前仍然开放的两件事

1. **3D 观感**：设置里已可切「深空 / 暖金」。再要更具体的效果（更亮/更暖/更慢/更多粒子/更强中心聚焦），

   用户会话下的设备列表与「退出其他设备」需要一次真实用户登录复核（破坏性动作未执行）。

## 十二、共享机上的时间类断言：该判「inconclusive」，不该判「红」

`.398` 收尾时连跑三次军团套件，全都没过，但**每次红的项都不同**：

| 次 | 起始 load1 | 结束 load1 | 失败项 |
|---|---|---|---|
| 1 | 12.28 | — | 导航断言（URL 5s 内变 `/org`） |
| 2 | 20.63 | — | `perf:denseMedianFrame` |
| 3 | 7.66 | **19.82** | `perf:denseMedianFrame` + `tour:yawSettlesWithin500ms` |

三次全是时间/帧率类，且 `.398` 的 diff 只碰设置页登录设备卡片（与 `/legion/3d` 零交集）。
同机还有三个 `bun` 进程在 65–100% CPU 上跑（其他节点的构建/测试）。

**结论**：在这台机器上，「红」与「机器忙」目前无法区分。正确做法不是放宽阈值，而是：

1. 断言记录**测量时刻的 `load1`**；
2. `load1` 超过经验阈值（如 > 8）时，结果标 `inconclusive` 并**自动重采样**，最多 N 次；
3. 发布门槛写死：**必须存在一次全绿运行，且该次测量期间 `load1 < 8`**；`inconclusive` 不算通过；
4. 若长时间拿不到安静窗口，由人决定「继续等」还是「接受行为断言绿 + 时间断言 inconclusive」——决定要写进发布记录。

反面做法（今晚我明确没做的）：放宽帧率阈值、加长超时、拿上一版的结果给新版背书。

# 附二：2026-11-07 的方法论（比版本本身更值得带走）

## 十六、串联验收有盲区：第一套红，后面十几套根本没跑

`run-<N>-final-acceptance.py` 是**串联**的：第一个失败套件之后直接中止。
`.398`/`.399` 都栽在 legion（第 5 个），于是**后面 15 套从未运行**。

我一度把 `.397` 的「20 套全绿」当成 `.398/.399` 的数字往外报——这是错的，已更正。
**做法**：需要局部证据时，用每个套件自己的 runner 单独跑（`deploy/run-*-acceptance.py --label <suite>-<N>`），
19 套可以在 legion 未通过的情况下拿到完整证据。

## 十七、源码级验证 ≠ 产物级验证

线上跑的是 `releases/preview.<N>-<sha>` 里的构建产物，不是工作区源码。CSS 会被打包、chunk 会拆分。
**做法**：修复必须在**发布产物**上再验一遍（本文档中 `.399` 的设备列表修复与角标行高都做了产物级验证）。

## 十八、对照实验必须同数据量、同负载、交替轮换

我曾用「候选版本连模拟 Hub（1 节点）」对比「生产连真实 Hub（393 节点）」，
得出「候选快 4 倍」的错误结论。正确做法：
- 两边连同一个 Hub（页面显示的节点数一致）
- 交替轮换多轮（A→B→A→B），各自记录 `load1`

实测结果（354 节点）：生产 `.397` 66.7 / 50.1 ms，候选 `.399` 66.7 / 66.6 ms —— 无回归。

## 十九、装置缺陷清单（今晚 8 次，全部造成过假结论）

| # | 装置问题 | 制造的假象 |
|---|---|---|
| 1 | 在 `npm run build` 之前启动的服务上测布局（CSS chunk 404） | 「390 下溢出 34/29/42px」 |
| 2 | 夹具用 `"on" in path` 判断开关（`?on=0` 也命中） | 「关不掉失败模式」 |
| 3 | 探针每次导航都清 localStorage | 「持久化失效」 |
| 4 | 双击坐标在负载下失效（未确认命中） | 「导航断言失败」×9 |
| 5 | 模拟 Hub 缺 `/health`（Dashboard 走 hub 根路径） | 「零节点却显示 Hub 不可达」 |
| 6 | 子 shell 里 `PATH` 未导出 | 「服务没起来」 |
| 7 | 探针指向已废弃端口、夹具缺开关 | 导航到 chrome-error |
| 8 | 对照实验两边数据量不同（1 vs 393 节点） | 「新版本快 4 倍」 |

**共性**：每一次都表现为「产品坏了」。检验顺序应当是 **先怀疑装置，再怀疑产品**。

## 二十、时间类断言在共享机上的判定协议（已有正文第十二节，此处补实测）

- 空白页基线：load 8.58 时 `about:blank` 仍为 16.7ms（60fps）→ 浏览器没有被全局限帧；
- 3D 354 节点：load 10–12 时两版都是 50–67ms（15–20fps）→ 是渲染成本 + CPU 竞争，不是回归；
- 军团套件阈值 26ms（≈38fps）在 load>10 时**不可达**，故该断言应判 `inconclusive` 而非失败。
