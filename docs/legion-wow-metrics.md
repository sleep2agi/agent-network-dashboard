## 桌面为什么只用一半宽度（答疑，避免被当成缺陷）

```
1440 视口安全区 1184×729（横向 1.62 : 1），而内容包围盒 631×736（0.86 : 1）
⇒ 内容比安全区"更竖"：外圈 Agent、三层部门盘在屏幕上纵向堆叠（层高 ×1.3）
⇒ 取景按高度贴边（102%），宽度自然只用 53%
⇒ 想再用掉横向空间，只有两条路：改俯角（更扁 → 更矮更宽）或改层高（削弱深度）—— 都是取向问题
```

## 指标 4 的相位拆解（`.559` 实测，1440）

| 相位 | 时刻 | 说明 |
|---|---|---|
| DOMContentLoaded | 77ms | 传输+解析不是瓶颈 |
| 第一帧（canvas 有尺寸） | **195ms** | **渲染不是瓶颈** |
| 编制就绪（节点 >100） | **4754ms** | 全在等 `/api/hub/people` |
| 入场 开始 → 结束 | 2011 → 3199ms | 入场本身约 1.2s |
| 取景收束 | 6927ms | 健康横幅的 `task-stats`（2508ms 发起、1277ms）晚到触发一次重取景 |

Hub 侧（同一轮）：

```
/api/hub/people      起始 1500ms  耗时 2117ms   ← 编制就绪等它
/api/hub/messages    起始 1498ms  耗时 2114ms   ← 与 people 同时抢 Hub
/api/hub/overview    起始 1497ms  耗时 1436ms
/api/hub/departments 起始 1502ms  耗时  183ms
/api/hub/task-stats  起始 2508ms  耗时 1277ms   ← 健康横幅
```

```
⇒ 首屏慢的敌人是 Hub 串行（people 与 messages 各 2.1s、同刻发起），不是渲染
⇒ 客户端可做的两件事：
   ① 军团路由延后非首屏请求（messages / overview / task-stats），把 Hub 让给 people
   ② 健康横幅的 task-stats 延后/合并，避免晚到再触发一次重取景（收束从 3.2s 推到 6.9s）
⇒ 更根本的在 Hub 侧（并发下发），证据已转 通信欧
```

> 一次 A/B（`?deferChrome=1` vs 基线）因相位探针自身采样不稳（同一命令两次运行，
> 一次 `编制就绪` 读不到、另一次全部相位为空）**判为无效，不作结论** ——
> 需要先把探针的"节点数门限 + 收束"逻辑改对，再谈开关是否有效。

### 相位实验记录（`.559`，全部 6/6 有效样本）

| 条件 | `/api/hub/people` 耗时 | 编制就绪 |
|---|---|---|
| 基线 #1 | 1822ms | 4387ms |
| 基线 #2 | 1322ms | 3577ms |
| 基线 #3 | 1322ms | 3577ms（同上轮） |
| `?deferChrome=1` | 1908ms，但**起点被推迟 3.7s** | **7974ms**（更慢） |
| 掐断 `/api/hub/messages` | 193ms（但请求起点被推到 6088ms） | 7540ms |
| 掐断 `/api/hub/overview` | **296ms** | 1822ms |
| 掐断 `/api/hub/messages`（另一轮对照） | 296–1932ms 区间 | — |

```
结论（只写能站住的）：
  · `?deferChrome=1` 让首屏更慢（起点整体后移）⇒ 这条开关不能拿来做军团优化
  · `/api/hub/people` 单次耗时波动极大：**296ms – 1932ms（≈6.5×）**
    ⇒ Hub 侧的耗时受并发/负载影响剧烈，单次 A/B 不足以判断"掐掉某个请求是否有用"
  · 掐断实验里多次出现"请求起点被推后 5s"，说明仍有一条未知的串行依赖（不是简单的并发争抢）
⇒ 下一步方法（未执行）：每个条件跑 5 次取中位数，再比较；单次读数一律不作结论
```

更根本的解法仍在 Hub 侧（并发下发 + 合并 people/messages 的首屏请求），证据已转 通信欧。
