# Dashboard 侧所需的接口合同草案（节点生命周期 / 模型切换）

> 目的：客户端正在推进「模型切换」与「节点向导 / fork 节点」，Dashboard 侧目前只能只读。
> 与其等对方口头说明，不如先写下"我们要什么"——对方只需确认/修正，来回一次就能对上。
> 现状：这两个能力在本仓库**没有任何代理路由**（`app/api/hub/` 下无 model/start/stop/restart/delete/takeover），
> 因此这里写的是**待建合同**，不是既有实现。

## 一、模型 / 思考深度切换

客户端判据（`#4820` 收口卡）是"切换后真发一条消息，从 runtime 日志 / 响应头确认走的是新模型"。
Dashboard 若要提供同样的能力，最少需要：

| # | 需要的能力 | 期望形态 | 我方用途 |
|---|---|---|---|
| 1 | 列出某节点可用 Provider / 模型 | `GET /api/nodes/{ref}/models` → `{ ok, providers: [{ id, models: [{ id, label, contextWindow? }] }], current? }` | 渲染选择器，且**只能显示服务端真实目录**，不猜模型名 |
| 2 | 读取当前生效的模型与思考深度 | 同上响应里的 `current: { providerId, modelId, effort? }` | 首屏显示"现在用的是哪个"，而不是只改文案 |
| 3 | 写入切换 | `PATCH /api/nodes/{ref}/model`，body `{ providerId, modelId, effort? }` → `{ ok, applied: {...}, effectiveAt }` | 切换后必须回读"实际生效值"，不能以请求 200 当成功 |
| 4 | 权限 | 明确"谁能对哪个节点切换"（owner / admin / 同网络成员？），拒绝时返回稳定错误码（如 `forbidden_not_owner`） | Dashboard 据此决定按钮可点性，不伪造 |
| 5 | 失败语义 | 切换失败要能区分：模型不存在 / runtime 不支持 / 节点离线 / 无权限 | 前端给出可核验原因，而不是"切换失败" |

> Dashboard 的额外要求（来自过去两次教训）：**不能自动回退到别的模型或新会话**——
> 若切换未生效，就停在原模型并显式报错。

## 二、节点生命周期写操作

| # | 需要的能力 | 期望形态 | 我方用途 |
|---|---|---|---|
| 1 | 启动 / 停止 / 重启 | `POST /api/nodes/{ref}/{start|stop|restart}` → `{ ok, state, taskId? }` | 节点详情页的生命周期按钮 |
| 2 | 删除 | `DELETE /api/nodes/{ref}`，需二次确认与"不可逆"标记 | 删除入口；Dashboard 必须锁定准确 ref（alias / node_id / 目录三者分开） |
| 3 | 接管（attach / takeover 既有节点） | 明确"支持 / 不支持"，以及支持时的前置条件（版本、runtime、已有会话处理） | 决定是否给出入口；**不支持就不显示按钮** |
| 4 | 权限 | 与模型切换同一套权限模型；拒绝码稳定 | 同上 |
| 5 | 异步语义 | 长操作给 `taskId` + 可查询状态（`GET …/tasks/{id}`），失败要带原因 | 前端显示进度而非转圈 |
| 6 | 幂等 | 重复 start 同节点不应报 500；重复 delete 应返回"已删除" | 防止重试把界面搞坏 |

## 三、我方愿意先做的部分（合同就位前不做的部分）

```
可以先做：UI 骨架 + 权限/降级状态的展示逻辑 + 只读字段（模型目录、当前模型、节点状态）
不做       ：任何会写库或"看起来能点"的假按钮；不在前端伪造 managed / 接管状态
```
